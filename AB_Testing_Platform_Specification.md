# 🔍 Project Specification: ExpAgent — Experiment Audit & Quality Agent

> **Что это:** Open-source инструмент, который подключается к хранилищу результатов A/B-тестов компании и находит эксперименты с методологическими ошибками: ложные победы из-за подглядывания, сломанные сплиты, ratio-метрики без дельта-метода, множественные сравнения без поправок.
>
> **Что это НЕ:** Не очередной дашборд A/B-тестов (есть GrowthBook), не «AI-саммари одного теста» (есть Statsig, Amplitude, PostHog). Не стартап.
>
> **Для чего:** Портфолио-проект на стыке Product Analytics + Applied ML/LLM для позиции аналитика / AI Analytics Engineer.

---

## 1. Почему не «ещё один калькулятор A/B-тестов»

### 1.1. Рынок «AI объясняет тест» уже красный

| Платформа | Что уже умеет (2025–2026) |
|:---|:---|
| **Statsig** (куплен OpenAI за $1.1B) | AI-саммари эксперимента с рекомендацией «катить или нет» |
| **Amplitude** | AI-отчёт по эксперименту с бизнес-эффектом |
| **PostHog AI** | Создаёт эксперимент по текстовому запросу, объясняет результат |
| **GrowthBook** | AI-саммари, MCP-сервер, ассистент со скиллом анализа |
| **Optimizely Opal** | Агент, который оценивает программу экспериментов целиком |
| **Eppo** (куплен Datadog) | Эксперименты внутри observability-платформы |
| **Trisigma** (Авито) | Российская платформа на Yandex AI Studio |
| **ClickHouse Agentic Stack** | Open-source: MCP-сервер, чат, трейсинг агента |

Делать «ещё один AI-саммари одного теста» — значит конкурировать с компаниями, у которых сотни инженеров и миллиарды долларов.

### 1.2. Где реальная незакрытая боль

Все перечисленные платформы анализируют **один текущий тест**. Но в компаниях, которые тестируют годами, накопились десятки и сотни завершённых экспериментов. И никто не проверяет их задним числом.

**Реальная проблема:** CPO приходит к аналитикам и спрашивает:
> *«Мы за 2 года провели 120 тестов, заявили суммарный эффект +28% на выручку. Но выручка выросла только на 9%. Где остальные 19%?»*

Ответ почти всегда один: **значительная часть «побед» были статистическим шумом**, вызванным:
- Подглядыванием (остановка теста в первый зелёный день без sequential testing).
- Ratio-метриками без дельта-метода (занижение дисперсии → ложная значимость).
- Множественными метриками без поправок (10 метрик → ~40% шанс случайного срабатывания).
- Незамеченными SRM (сломанный сплит, результат которого принят за победу).
- Тестами с нереалистичным MDE (заявили эффект +0.5% при выборке, которая ловит только +3%).

**Это и есть наш фокус: ретроспективный аудит качества экспериментов.**

## 2. Что конкретно делает продукт

### Сценарий использования:

1. Пользователь подключает агента к хранилищу результатов тестов (ClickHouse, PostgreSQL, CSV-архив, DuckDB).
2. Агент проходит по каждому завершённому эксперименту и прогоняет **чек-лист методологических ловушек**.
3. На выходе: структурированный отчёт с разбивкой:
   - Сколько тестов были «чистыми победами».
   - Сколько — **ложные победы** (с указанием конкретной ошибки).
   - Сколько — неубедительные (мощность не набрана).
   - Пересчитанный суммарный эффект программы экспериментов.

### Пример вывода агента:
```
═══════════════════════════════════════════════════════

  Total experiments analyzed: 87
═══════════════════════════════════════════════════════

  ✅ Clean wins (methodology correct):           31  (36%)
  ⚠️  Questionable wins (issues detected):       24  (28%)
  ❌ False wins (likely noise):                   14  (16%)

  Claimed cumulative effect:   +23.4%
  Adjusted cumulative effect:  +7.1%  (after removing false wins)

═══════════════════════════════════════════════════════
```

## 3. Чек-лист ловушек, которые ищет агент

### Ловушка 1: Подглядывание (Peeking Problem)
* **Что это:** Тест остановлен в первый день, когда p-value случайно упал ниже 0.05. При ежедневной проверке вероятность хотя бы одного ложного срабатывания за 14 дней достигает 25–30%.
* **Как детектируем:** Сравниваем фактическую длительность теста с минимально необходимой (рассчитанной из pre-experiment MDE и baseline variance). Если тест остановлен значительно раньше и не использовал sequential testing — флагаем.
* **Правильное решение:** Sequential testing (mSPRT / always-valid p-values).

### Ловушка 2: Ratio-метрики без дельта-метода
* **Что это:** Метрики вида «выручка на заказ», «клики на сессию», «конверсия в покупку среди посетителей товара» — это дроби, где и числитель, и знаменатель случайны. Обычный t-тест занижает дисперсию такой метрики, потому что игнорирует ковариацию между числителем и знаменателем.
* **Как детектируем:** Проверяем, является ли целевая метрика отношением двух агрегатов. Если да — пересчитываем дисперсию через Delta Method и сравниваем с заявленной значимостью.
* **Формула Delta Method для ratio $R = Y/X$:**
  $$\text{Var}(R) \approx \frac{1}{\bar{X}^2}\left[\text{Var}(Y) - 2R \cdot \text{Cov}(X,Y) + R^2 \cdot \text{Var}(X)\right]$$

### Ловушка 3: Множественные сравнения без поправки
* **Что это:** Тестируется 10 метрик одновременно (конверсия, выручка, время на сайте, retention...). При $\alpha = 0.05$ вероятность хотя бы одного ложного срабатывания: $1 - (1-0.05)^{10} \approx 0.40$ (40%!).
* **Как детектируем:** Считаем количество метрик в эксперименте. Если больше одной — применяем поправку Benjamini-Hochberg (FDR) и проверяем, выжил ли заявленный результат.

### Ловушка 4: SRM (Sample Ratio Mismatch)
* **Что это:** Техническая ошибка, из-за которой в группы попало неравное число пользователей.
* **Порог:** $p < 0.001$ (индустриальный стандарт; при $p < 0.01$ и ежедневных проверках будут регулярные ложные тревоги).
* **Тест:** $\chi^2$-критерий Пирсона.

### Ловушка 5: Недостаточная мощность (Underpowered Tests)
* **Что это:** Тест запущен на выборке, которая физически не может обнаружить заявленный эффект. Например, нужно 50 000 пользователей на группу, а набрали 5 000.
* **Как детектируем:** Pre-experiment power analysis: по baseline variance и заявленному MDE рассчитываем необходимый $N$ и сравниваем с фактическим.
* **Важно:** Мы **не считаем post-hoc power** (мощность по наблюдаемому эффекту). Это известная ловушка — post-hoc power есть монотонная функция от p-value и не несёт дополнительной информации.

### Ловушка 6: CUPED без проверки предпосылок
* **Что это:** CUPED применён, но ковариата из предпериода слабо коррелирует с метрикой теста ($\rho < 0.3$), или предпериод пересекается с периодом теста, или ковариата зависит от назначения в группу.
* **Как детектируем:** Проверяем корреляцию $\rho(X, Y)$, проверяем даты, проверяем баланс ковариаты между группами.

### Ловушка 7: Неверное использование статистических критериев
* **Что это:** Например, использование Mann-Whitney для оценки разницы средних (MWU проверяет стохастическое доминирование, а не разницу средних — это разные вещи). Или использование t-теста Стьюдента вместо Уэлча при неравных дисперсиях.
* **Как детектируем:** По типу метрики и свойствам распределения (асимметрия, разброс дисперсий) определяем, какой критерий был бы корректен, и флагаем расхождение.

## 4. Статистические инструменты (Tools)

Каждый инструмент — чистая детерминированная Python-функция. LLM вызывает их через Tool Calling / Function Calling и **не имеет права считать математику самостоятельно**.

```text
──────────────────────────────────────────────────────────────────
 SUITE 1: DATA INTEGRITY
──────────────────────────────────────────────────────────────────
 srm_check_tool           Chi-square, порог p < 0.001
 data_quality_tool        Проверка дубликатов, пропусков, пересечений групп

──────────────────────────────────────────────────────────────────
 SUITE 2: EXPERIMENT DESIGN VALIDATION
──────────────────────────────────────────────────────────────────
 pre_experiment_power_tool    Расчёт необходимого N по baseline stats и MDE
                              (НЕ post-hoc power!)
 duration_adequacy_tool       Хватило ли дней для набора выборки?

──────────────────────────────────────────────────────────────────
 SUITE 3: VARIANCE REDUCTION
──────────────────────────────────────────────────────────────────
 cuped_audit_tool         Проверка предпосылок CUPED:
                          - корреляция ковариаты
                          - баланс между группами
                          - отсутствие пересечения периодов
 winsorization_tool       Обрезка выбросов на заданном перцентиле

──────────────────────────────────────────────────────────────────
 SUITE 4: HYPOTHESIS TESTING (FREQUENTIST)
──────────────────────────────────────────────────────────────────
 welch_ttest_tool         Сравнение средних (user-level данные, не агрегаты!)
 proportion_ztest_tool    Сравнение конверсий (Z-test)
 fisher_exact_tool        Малые выборки (N < 30 конверсий)
 delta_method_tool        Корректная дисперсия ratio-метрик (revenue/orders)
 bootstrap_tool           Доверительные интервалы без предположения нормальности

──────────────────────────────────────────────────────────────────
 SUITE 5: SEQUENTIAL TESTING
──────────────────────────────────────────────────────────────────
 msprt_tool               mixture Sequential Probability Ratio Test
                          (always-valid p-values для безопасного подглядывания)

──────────────────────────────────────────────────────────────────
 SUITE 6: MULTIPLE TESTING CORRECTION
──────────────────────────────────────────────────────────────────
 benjamini_hochberg_tool  FDR-поправка при множественных метриках
 bonferroni_tool          Консервативная поправка (для guardrail-метрик)

──────────────────────────────────────────────────────────────────
 SUITE 7: BAYESIAN ENGINE
──────────────────────────────────────────────────────────────────
 bayesian_ab_tool         Chance to Win + Expected Loss
                          (Conjugate Beta-Binomial для конверсий,
                           Log-Normal для revenue)

──────────────────────────────────────────────────────────────────
 SUITE 8: BUSINESS TRANSLATION
──────────────────────────────────────────────────────────────────
 effect_to_revenue_tool   Перевод эффекта в деньги (входные параметры:
                          baseline revenue, traffic, эффект с CI).
                          Расчёт строго в Python, не в голове LLM.
```

### Критически важные принципы:
1. **Все тесты работают на user-level данных**, а не на агрегатах. Бутстрап, CUPED и Mann-Whitney физически не работают на агрегатах — им нужна строка на каждого пользователя.
2. **Арифметика перевода в рубли** выполняется в `effect_to_revenue_tool` (Python), а **не в голове LLM**. Агент передаёт параметры в функцию и получает готовый расчёт.
3. **SQL-запросы, которые генерирует LLM, логируются и доступны для ревью.** Мы честно признаём, что генерация SQL — главный источник ошибок агента (не арифметика), и обеспечиваем прозрачность.

## 5. Системный промпт агента (Parent Prompt)

### Протокол аудита эксперимента (SOP):
```
Ты — ведущий продуктовый аналитик, который проверяет корректность и интерпретирует A/B-эксперименты.
Подготовь проверяемый ответ на бизнес-вопрос конкретного теста: что изменилось, насколько надёжны данные,
подтверждена ли гипотеза и какое следующее действие обосновано. Пиши по-русски.
Используй доступные инструменты (Tools) для получения данных и вычислений.

1. УСТАНОВИ ПАСПОРТ ЭКСПЕРИМЕНТА И ПЕРИОД:
   - Сверь experiment ID, tracking key, фичефлаг, варианты, фактический статус, выбранную фазу.
   - Зафиксируй дату среза, окно набора когорты, окно конверсии и дату обновления результата.
   - Различай план из дизайна и фактически действовавшую конфигурацию.
   - При изменении весов используй ожидаемое распределение, действовавшее в соответствующий период;
     наблюдаемую долю участников НЕЛЬЗЯ подставлять как ожидаемую.
   - Если статус stopped/dnf — это не означает автоматически проигрыш или отсутствие эффекта.

2. СПЕЦИФИКАЦИЯ АНАЛИЗА И МЕТРИК:
   - Восстанови аудиторию, единицу рандомизации, момент первой экспозиции, исключения.
   - Выдели Primary/goals, Guardrails, Secondary и диагностические метрики.
   - Для нескольких рукавов перечисли заранее нужные сравнения (B–A, C–A, C–B).
   - В знаменателе метрик (CR, RPV) СОХРАНЯЙ ВСЕХ участников группы, включая тех, у кого 0 заказов.
     Не превращай отсутствие заказа в пропуск участника!

3. ПРОВЕРКА КАЧЕСТВА ДАННЫХ (DATA QUALITY):
   - Проверь N уникальных единиц по рукавам, динамику экспозиций, дубли, пропуски ID.
   - Проверь пересечения: наличие одного участника в нескольких вариантах.
   - Запусти srm_check_tool по исходному потоку до исключений и с ожидаемым сплитом фазы (порог p < 0.001).
   - Сравнивай когорты только с одинаково завершёнными окнами наблюдения (window maturity).
   - КРИТИЧЕСКИЙ ДЕФЕКТ: Если SRM нарушен или данные битые — выстави статус "данным доверять нельзя".
     Сохрани полезные описательные числа, но победителя НЕ объявляй!

4. ВЫЧИСЛЕНИЕ ЭФФЕКТОВ (СТРОГО ЧЕРЕЗ TOOLS):
   - Бинарная метрика → proportion_ztest_tool (или fisher_exact_tool для N < 30)
   - Непрерывная метрика → welch_ttest_tool
   - Ratio (дробь: выручка/заказы, RPV) → delta_method_tool (сравнить с naive SE)
   - Сильно скошенная с выбросами → bootstrap_tool + winsorization_tool
   - Предпериод доступен → cuped_tool (проверить отсутствие эффекта в предпериоде)
   - Метрик > 1 → benjamini_hochberg_tool (контроль FDR)
   - Ранняя остановка без sequential → ФЛАГ "PEEKING_RISK" (msprt_tool)

5. СФОРМИРУЙ ИТОГ, ПРИГОДНЫЙ ДЛЯ РЕШЕНИЯ:
   - Начни строго с одного из 5 канонических статусов:
     * «данным доверять нельзя»
     * «данных недостаточно»
     * «промежуточный результат»
     * «есть основания для следующего шага»
     * «есть признаки ухудшения»
   - 2–4 предложения: что проверено, главный эффект, ключевое ограничение и рекомендуемое действие человеку.
   - Паспорт эксперимента (таблица: ID, фаза, даты, сплит, движок).
   - Качество данных (таблица: проверка -> результат -> статус: проверено/не проверено/неприменимо).
   - Primary и Guardrails (таблица: метрика | контроль | тест | абс. эффект | отн. эффект | CI | p-value/posterior | вывод).
   - Бизнес-рекомендация и условия её пересмотра.

ЖЁСТКИЕ ЗАПРЕТЫ:
- ЗАПРЕЩЕНО считать p-value, CI, дисперсию, средние в голове. Только через Tools.
- ЗАПРЕЩЕНО выдумывать числа, результаты проверок, причины остановки и ссылки.
- ЗАПРЕЩЕНО считать post-hoc power (это переупакованный p-value).
- ЗАПРЕЩЕНО использовать Mann-Whitney для оценки разницы средних по выручке.
- ЗАПРЕЩЕНО исключать пользователей постфактум только ради получения красивого SRM.
```

exp-agent/
│
├── app.py                         # Streamlit: чат + audit dashboard + SQL лог
│
├── harness/                       # LLM-оркестрация
│   ├── agent.py                   # ReAct loop с Tool Calling
│   ├── system_prompt.py           # SOP из раздела 5

│
├── tools/                         # Детерминированные Python-функции
│   ├── srm.py                     # Chi-square (порог 0.001)
│   ├── power_analysis.py          # Pre-experiment power (НЕ post-hoc)

│   ├── delta_method.py            # Дисперсия ratio-метрик

│   └── sql_templates.py           # Шаблоны SQL (user-level, не агрегаты)

├── trap_suite/                    # 20 синтетических экспериментов-ловушек
│   ├── generator.py               # Генератор реалистичных данных
│   ├── traps/
│   │   ├── 01_clean_win.py        # Чистая победа (эталон)

│   │   ├── 15_aa_test_false_positive.py   # A/A тест, который "нашёл" эффект

## 7. Ключевая фича: Trap Suite (20 экспериментов-ловушек)

Это то, что **выделит проект среди всех аналогов** и впечатлит на собеседовании сильнее любого Streamlit-интерфейса.

### Идея:
Мы генерируем 20 синтетических, но реалистичных экспериментов, в каждый из которых **заложена конкретная методологическая ловушка** (или её отсутствие — эталонный чистый тест). Агент должен правильно классифицировать каждый.

### Зачем это нужно:
1. **Доказательство компетентности агента.** Не «он что-то считает», а «он корректно нашёл 19 из 20 ловушек».
2. **Доказательство твоей компетентности.** Чтобы заложить ловушку, нужно глубоко понимать, почему она ловушка. На собесе ты объясняешь каждый кейс.
3. **Регрессионное тестирование.** При изменении промпта или модели — прогоняешь Trap Suite и проверяешь, не сломалось ли что-то.

### Формат:
```python
# trap_suite/traps/04_ratio_without_delta.py

def generate():
    """
    Ловушка: метрика 'revenue_per_order' — это ratio.
    Обычный t-тест покажет p=0.03 (значимо).
    Delta method покажет p=0.12 (незначимо).
    Правильный вердикт: FALSE_WIN (ratio без дельта-метода).
    """
    # ... генерация user-level данных ...
    return {
        "data": df,
        "metadata": {
            "metric_type": "ratio",
            "metric_name": "revenue_per_order",
            "claimed_result": "significant",
        },
        "expected_verdict": "FALSE_WIN",
        "expected_flags": ["RATIO_WITHOUT_DELTA_METHOD"],
    }
```

## 11. На какие вопросы собеседования ты теперь готов

1. **«Чем это отличается от GrowthBook / Statsig / PostHog AI?»**
   → Они анализируют один текущий тест. Мы делаем ретроспективный аудит всей программы экспериментов и ищем ложные победы. Разный use case.

2. **«Почему не просто скрипт по крону?»**
   → Для фиксированного пайплайна из 5 проверок — да, крон. Но аудит требует адаптации под разные схемы хранения, типы метрик и контекст. LLM нужна для генерации SQL под конкретную схему и для human-readable отчёта. При этом мы честно говорим: SQL-генерация — главный источник ошибок, поэтому все запросы логируются.

3. **«Post-hoc power — это же ловушка?»**
   → Именно. Поэтому мы принципиально не считаем post-hoc power. Мы используем pre-experiment power analysis: оцениваем необходимый N по baseline variance и заявленному MDE до теста и сравниваем с фактическим N.

4. **«Можно ли использовать Mann-Whitney для выручки?»**
   → MWU проверяет стохастическое доминирование (P(X > Y) > 0.5), а не разницу средних. Для денежных решений нужна именно разница средних. Мы используем Welch t-test с winsorization или bootstrap для скошенных метрик.

5. **«А что насчёт комплаенса?»**
   → Для компаний с чувствительными данными (медицина, финтех) предусмотрен режим с локальной LLM (Qwen/Llama). Данные не покидают периметр. Мы не обещаем «подключить за вечер к Генотеку» — это инфраструктурный проект с участием InfoSec.
